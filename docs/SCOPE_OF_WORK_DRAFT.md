# A freelance website scope of work: an annotated example

**Unpublished editorial draft. Owner approval required before publication.** Compare this draft with the existing scope-creep article before deciding whether to publish a separate guide or fold the example into that article. No ranking or conversion benefit is claimed.

Suggested description: A practical five-page website scope example covering deliverables, revision limits, client inputs, approval and extra requests.

A project scope should let you and your client answer the same question: what will be delivered for the agreed price? “A business website” leaves room for different expectations. A list of named pages, included tasks and revision rules gives both sides something concrete to review.

The fictional example below is for a freelancer designing a five-page brochure website. Adapt the details to the work you actually offer. It does not set a market rate or prescribe a contract.

## 1. Start with the outcome

**Example scope text:**

> Design and build a responsive brochure website for Northstar Design, with Home, About, Services, Work and Contact pages. The purpose is to explain the business and make it easy for potential clients to send an enquiry.

Why this helps: the outcome sets a direction, while the page list makes the deliverable count visible. “Five pages” alone is less useful if nobody has agreed which five pages they are.

## 2. Describe what each deliverable includes

| Deliverable | Included in this example | Not included in this example |
| --- | --- | --- |
| Page design | One agreed visual direction applied across five pages | A second brand direction or a separate logo project |
| Website build | Responsive layouts for the five named pages | Ecommerce, customer accounts or a booking system |
| Contact page | Business contact details and one enquiry form | A customer support inbox or automated sales sequence |
| Content placement | Client-supplied text and images placed on the pages | Writing all page copy or commissioning photography |
| Handover | One handover call and agreed access details | Ongoing content updates or maintenance |

The exclusions are as important as the inclusions. They are not a reason to refuse useful work; they show which requests need a separate discussion about price and time.

## 3. Define a revision round before the first review

**Example scope text:**

> Two revision rounds are included for the agreed five-page design. A round means one consolidated list of feedback from the client's nominated contact. Revisions adjust the agreed direction; a new page, new brand direction or new functional requirement is assessed as extra work.

Make the examples specific to your project. Changing a heading, adjusting spacing or replacing a supplied image can fit within a revision round. Adding a sixth page or replacing the brochure site with an online shop changes the deliverables.

Do not turn the definition into a surprise after feedback arrives. Review it with the client while agreeing the scope, and record which round each consolidated feedback list belongs to.

## 4. Record the inputs and dependencies

**Example scope text:**

> The client supplies final page copy, business contact details and approved images before the build begins. One nominated contact gathers feedback and confirms approvals. Hosting and domain access must be available before the agreed handover step.

A timeline is easier to manage when it names the things you need. Use actual dates once they are agreed. If an input is late, discuss the impact and record a revised delivery date rather than silently keeping an impossible deadline.

## 5. Keep scope approval separate from later requests

Before starting, ask the client to review the named deliverables, exclusions, included revisions, dates and payment milestones together. Give them a clear opportunity to correct misunderstandings.

Keep the approved version and the decision record. An approval is useful evidence of the agreed starting point, but it does not stop a client from having new ideas. The next step is to handle those ideas visibly.

## 6. Show how an extra request changes the project

Suppose the client asks for a Testimonials page after approving the five-page scope. A useful response acknowledges the request and explains the next decision:

> Yes, we can add a Testimonials page. It is an additional page beyond the five we agreed. I'll send a change order with the extra deliverable, price and timeline impact so you can review it before I start.

The change order should identify the new work, its price, any additional days and the client's decision. Use your own agreed commercial terms; there is no universal “correct” price for an extra page. Record the approval before treating the additional work as part of the project.

## A final scope review

Before you send the scope, check that someone unfamiliar with the project can answer:

1. What exactly will be delivered?
2. Which tasks and costs are excluded?
3. What does one revision round mean, and how many are included?
4. What must the client supply, and when?
5. Who gives consolidated feedback and approval?
6. How will extra requests be priced and approved?
7. Where can both sides find the approved scope and later changes?

You can use this structure in a document or in a project workspace. ScopeFlow supports deliverables, revision limits, client approval links and change orders if you want to keep those records together. Start with the agreed scope; choose the tool that makes it easiest to keep that agreement clear.
